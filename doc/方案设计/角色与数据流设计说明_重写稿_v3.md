# 角色与数据流设计说明

**课题：** 面向大众民事的联盟链电子公证存证系统设计与实现  
**用途：** 概要设计说明书、数据库设计说明书的前置梳理材料  
**设计依据：** 2026-11-19 定稿《本科毕业论文（设计）任务书与开题报告》  
**版本：** 重写稿 v3  
**说明：** 本文统一系统角色、业务流程、链上链下数据边界和关键状态处理。具体类名、字段名、合约变量名及 API 路径以编码时的接口设计为准；本文不把尚未联调的实现细节写成已验证事实。

## 1. 系统定位与总体结构

### 1.1 系统要解决的问题

系统面向个人民事活动中的凭证保全需求，覆盖四类场景：

1. 民间借贷；
2. 房屋租赁；
3. 简易民事协议；
4. 原创内容版权。

用户上传凭证文件并填写相应场景信息。后端计算文件摘要，将原始文件加密后保存在 MySQL，并把文件清单的聚合摘要及必要凭证信息登记到 FISCO BCOS 联盟链。用户可以向指定核验方签发授权；核验方在授权范围内进行材料核验、查看或下载时，系统先通过合约检查授权，再将相应操作记入链上。系统另提供回执复核功能，用于检查第三方手中的回执 PDF 是否与链上登记的回执摘要一致。

系统的核心流程是：

**用户提交材料 → 后端计算摘要并加密保存 → 聚合摘要上链 → 用户签发授权 → 核验方按授权使用材料 → 生成回执并支持第三方复核。**

这里的“存证”是对文件内容摘要及相关记录进行链上登记，不代表系统能够证明文件在上链前就是真实的，也不等同于司法公证。

### 1.2 技术架构

系统采用前后端分离、后端单体部署的结构：

| 层次 | 主要技术 | 主要职责 |
|---|---|---|
| 前端 | Vue 3、Vite、Element Plus | 用户交互、场景表单、文件上传、授权管理、回执展示与下载 |
| 后端 | Spring Boot、MyBatis-Plus、JWT | 用户身份认证、业务校验、流程编排、文件处理、数据库访问、调用区块链 |
| 数据库 | MySQL 8 | 用户信息、凭证元数据、加密文件、逐文件摘要、授权关联、操作记录、回执文件 |
| 区块链 | FISCO BCOS 3.x，单机 4 节点 PBFT | 登记凭证摘要、保存授权状态、记录授权范围内的核验及访问操作、登记回执摘要 |
| 智能合约 | Solidity，单个 EvidenceStore 合约 | 实现存证登记、授权签发与撤销、访问记账、凭证失效、回执摘要登记 |

后端通过 `ChainGateway` 一类的服务封装区块链调用。业务代码不直接散布 SDK 调用，便于将开发阶段的模拟链实现与最终真实链实现隔离。

### 1.3 谁负责提交链上交易

本课题采用**平台托管账户代发交易**的方式。存证用户和核验方不需要创建区块链账户、持有私钥或支付 gas。

| 操作 | 业务发起者 | 链上交易实际提交者 |
|---|---|---|
| 存证登记 | 存证用户 | 平台存证服务账户 |
| 签发授权 | 存证用户 | 平台授权服务账户 |
| 撤销授权 | 存证用户 | 平台授权服务账户 |
| 核验、查看、下载的授权记账 | 核验方 | 平台核验服务账户 |
| 回执摘要登记 | 存证用户申请 | 平台存证服务账户 |
| 回执复核 | 任意持有回执的人 | 不提交交易，只读查询 |

因此，链上交易的 `msg.sender` 是平台账户，不是最终用户本人。平台通过登录账号、JWT 和业务权限校验确认是谁发起了操作；链上记录则用于证明相应交易及其状态确实被写入联盟链。系统不把平台代发交易描述成用户个人钱包签名。

## 2. 系统角色与权限边界

系统按业务职责划分为三类角色。

| 角色 | 典型身份 | 可以进行的操作 | 不具有的权限 |
|---|---|---|---|
| 存证用户 | 上传借条、租赁材料或协议的个人 | 管理本人凭证；上传材料；填写场景信息；签发、撤销授权；申请生成回执；查看本人凭证的操作留痕；按规定申请删除 | 不能修改已经登记在链上的摘要；不能直接操作其他用户的凭证 |
| 核验方 | 纠纷相对人、调解员、律师等被授权人员 | 使用用户提供的存证编号和本人授权标识，在授权范围内核验材料、查看或下载原文；上传回执进行只读复核 | 未获授权时不能核验、查看或下载受保护的原始材料；不能修改授权状态 |
| 平台管理员 | 本课题中由开发者承担部署和运维职责 | 管理用户状态和角色；维护系统配置；查看链连接状态与交易信息；执行合约部署、服务账户白名单维护、备份和巡检 | 普通管理页面不提供直接修改链上存证记录的能力；管理员操作受系统权限和审计记录约束 |

### 2.1 存证用户与核验方的关系

存证用户是凭证的提交者和授权决定者。核验方不是凭证所有者，只有在存证用户签发授权后，才能按授权范围使用对应凭证。

授权至少包括：

- 对应的存证编号；
- 被授权方标识 `verifierId`；
- 授权有效期；
- 可使用次数；
- 撤销状态。

`verifierId` 是系统用于关联授权对象的假名化标识，不直接使用姓名、手机号、身份证号等身份明文。平台负责维护账号与该标识之间的对应关系。若该映射能够关联到具体个人，仍应按个人信息进行管理。

### 2.2 平台管理员的权限边界

平台管理员负责部署和维护系统，不代表管理员可以任意代替用户作出授权决定。签发授权时，后端必须验证当前登录用户是否为该凭证的创建者，再由平台账户提交链上授权交易。

平台在技术上能够接触服务端密钥并解密文件，因此系统采用的是**服务端密钥托管模式**，不是端到端加密。该信任前提应在论文中如实说明，不能表述为平台自身无法读取用户原文。

## 3. 存证用户的数据流

### 3.1 用户操作顺序

```text
注册 / 登录
    │
    ▼
选择存证场景、填写场景信息、上传文件
    │
    ▼
后端计算逐文件摘要、生成清单聚合摘要
    │
    ▼
逐文件加密，密文及相关数据写入 MySQL
    │
    ▼
提交聚合摘要登记交易
    │
    ▼
链上确认后，凭证状态变为“已上链”
    │
    ├── 签发授权 ──► 核验方可按授权范围使用凭证
    │
    ├── 申请回执 ──► 生成 PDF 并登记回执摘要
    │
    └── 查看留痕 / 申请删除
```

### 3.2 上传与存证登记

以民间借贷场景为例，用户上传聊天截图和电子借条 PDF。系统按以下步骤处理：

| 步骤 | 前端 | 后端 | MySQL | 联盟链 |
|---|---|---|---|---|
| 1. 提交 | 用户选择场景、填写字段并上传文件；页面展示个人信息处理告知 | 接收请求，检查登录状态、文件类型、文件大小和场景字段 | — | — |
| 2. 计算摘要 | 展示处理中状态 | 对每个文件计算 SHA-256，得到逐文件摘要 | — | — |
| 3. 计算聚合摘要 | — | 将逐文件摘要按摘要值升序排列，再按固定长度编码拼接后计算 SHA-256，得到清单聚合摘要 | 保存逐文件摘要及聚合摘要 | — |
| 4. 加密文件 | — | 每个文件生成独立随机 DEK，使用 AES-256-GCM 加密；AAD 绑定存证编号和随机文件标识 | 保存密文、IV、认证标签及包裹后的 DEK | — |
| 5. 写入待登记数据 | — | 在数据库事务中保存凭证、文件和场景字段，初始状态设为待上链 | 保存密文 LONGBLOB、摘要、元数据等 | — |
| 6. 提交登记 | 页面显示处理中 | 通过 ChainGateway 提交登记交易 | 等待链上确认后更新交易哈希、区块高度和状态 | 登记存证编号、聚合摘要、场景类型和算法标识 |
| 7. 确认结果 | 展示存证编号、摘要及登记状态 | 查询交易回执或链上记录，确认登记结果 | 状态更新为已上链 | 保存登记记录 |

#### 聚合摘要规则

一份凭证可以包含一个或多个文件，但至少包含一个文件。每个文件先独立计算 SHA-256 摘要，再对摘要值排序，按固定长度编码后拼接并计算最终聚合摘要。

该规则具有以下含义：

- 文件名不参与聚合摘要计算；
- 文件上传顺序不影响聚合摘要；
- 文件内容变化会改变对应文件摘要；
- 文件数量变化或重复文件的数量变化会改变摘要集合；
- 链上只登记聚合摘要，逐文件摘要保存在 MySQL，用于后续差异定位。

这里采用的是基于逐文件摘要集合的聚合方式，不使用 Merkle 树。

#### 链上登记失败或超时

数据库写入与链上交易不属于同一个分布式事务。系统先将凭证及密文保存为待上链状态，再提交链上交易。

如果交易明确失败，凭证不能标记为已上链；如果出现超时或响应丢失，后端应先根据交易哈希、存证编号查询链上状态，再决定是否重试。不能仅因接口超时就直接重新生成一笔登记交易，也不能把“数据库已保存”当作“链上存证已完成”。

只有获得链上确认并完成必要的状态核对后，凭证才进入“已上链”状态，才允许生成正式回执。

### 3.3 授权签发与撤销

存证用户在本人凭证详情页中填写核验方标识、授权有效期和使用次数。后端先验证：

1. 当前用户已登录；
2. 当前用户是该凭证的创建者；
3. 授权参数合法；
4. 凭证处于允许授权的状态。

验证通过后，后端调用合约提交授权交易。合约保存凭证编号、假名化核验方标识、有效期、使用次数和撤销状态。授权交易确认后，后端更新本地授权记录。

撤销授权时，后端同样先验证凭证归属，再提交链上撤销交易。链上撤销状态是授权是否有效的最终依据；MySQL 中的授权记录用于页面展示和查询，不应被当作独立于链上状态的最终授权依据。

### 3.4 回执生成

回执采用两阶段处理，以避免回执摘要包含自身登记交易信息而形成循环依赖。

**第一阶段：生成最终 PDF。**

原始凭证聚合摘要上链成功后，系统使用已确认的存证编号、原始登记交易哈希、区块高度、逐文件摘要、聚合摘要、场景信息和时间说明生成 PDF。区块时间与用户声明的业务时间应分别展示，不能把用户填写的业务时间说成链上可信时间。

**第二阶段：登记回执摘要。**

系统对第一阶段生成的最终 PDF 原始字节计算 SHA-256，得到回执摘要，再通过合约建立“存证编号—回执摘要”的对应关系。每个存证编号的回执摘要只允许登记一次。

PDF 原始字节、回执摘要及存证编号保存在 MySQL。用户后续下载时，系统直接返回已保存的 PDF 原件，不重新渲染。若回执摘要登记交易超时或响应丢失，应查询原交易状态；重试时沿用同一份 PDF 和同一个摘要，不重新生成另一份内容。

回执不做数字签名。回执登记交易自身的哈希和区块高度属于系统内部核对信息，不作为回执正文中的必要展示内容。

### 3.5 查看操作留痕与删除申请

存证用户可以查看本人凭证对应的授权使用记录，包括核验方标识、操作类型、操作时间和处理结果。该记录以链上事件为依据回灌到 MySQL，供页面查询。

用户申请删除凭证时，系统需要处理链上和链下两部分：

- 链下：删除对应的加密文件、包裹后的数据密钥以及不再需要保留的身份关联数据；
- 链上：将凭证标记为失效，并撤销或阻断该凭证下尚未结束的授权；
- 后续访问：该凭证的核验、查看和下载请求均应被拒绝；
- 审计：在链下审计日志中记录删除申请及处理结果。

链上已经写入的历史记录不能直接删除，因此系统不能宣称实现了链上数据的彻底删除，也不能把删除密钥等同于完全履行所有删除义务。具体法律边界应按任务书与开题报告中的个人信息保护法口径表述。

## 4. 核验方的数据流

本系统中有两种目的不同的操作，必须明确区分：

1. **授权使用凭证：**核验方希望核验原始材料，或在授权范围内查看、下载原文。这些操作需要存证用户事先授权，并且需要链上记账。
2. **复核回执：**任何持有回执 PDF 的人，都可以检查该 PDF 是否与链上登记的回执摘要一致。这是只读操作，不需要授权，也不消耗授权次数。

两者不是同一个流程，不能把“回执复核”说成“原始材料核验”。

### 4.1 授权范围内的核验、查看与下载

核验方取得存证编号和授权时使用的 `verifierId` 后，可以在授权范围内发起以下操作：

| 操作类型 | 目的 | 是否需要授权 | 是否写链 | 是否扣减次数 |
|---|---|---:|---:|---:|
| 材料核验 `VERIFY` | 上传核验方持有的材料，与存证时登记的摘要进行比对 | 是 | 是 | 是 |
| 查看原文 `VIEW` | 查看平台保存的原始材料 | 是 | 是 | 是 |
| 下载原文 `DOWNLOAD` | 下载平台保存的原始材料 | 是 | 是 | 是 |

三类操作共用授权使用次数，但链上事件通过 `actionType` 区分具体操作。

#### 材料核验流程

```text
核验方输入存证编号、verifierId，并上传待核验材料
    │
    ▼
后端检查登录状态及本地授权信息
    │
    ▼
后端进行只读预检：是否存在授权、是否过期、是否撤销、次数是否可能已用尽
    │
    ▼
后端重新计算核验方上传材料的逐文件摘要
    │
    ▼
先用 MySQL 中保存的逐文件摘要重算聚合摘要，并与链上登记值核对
    │
    ▼
确认链下摘要清单与链上登记值一致后，再比较双方逐文件摘要集合
    │
    ▼
提交链上授权记账交易
    │
    ▼
合约再次检查授权状态并原子扣减次数，记录 actionType 和核验结果
    │
    ▼
交易成功后，后端返回核验结果并保存查询记录
```

后端的预检只用于尽早发现明显无效的请求，避免不必要的链上交易。授权是否最终有效，以合约执行时读取的链上状态为准。若预检通过后授权恰好被撤销或过期，合约仍应拒绝该次交易。

#### 为什么要先核对 MySQL 摘要清单

链上登记的是聚合摘要，MySQL 保存逐文件摘要。若直接拿 MySQL 中的逐文件摘要与第三方材料比较，而不先核对其聚合结果，就无法排除 MySQL 中的摘要清单已被单独篡改。

因此必须分两步：

1. 根据 MySQL 中保存的逐文件摘要重新计算聚合摘要，并与链上登记值比较；
2. 只有第一步一致，才将第三方上传材料的摘要集合与该逐文件摘要集合比较，定位新增、缺失或内容不同的文件。

差异比较以摘要多重集合为基础，保留重复文件的数量信息。文件名或上传顺序变化不应被判定为文件内容变化。

#### 授权扣次与留痕

材料核验、查看原文和下载原文均需在内容返回前完成链上记账。合约在同一笔交易中完成授权有效性检查、使用次数扣减和事件记录。授权无效、已撤销、已过期、次数用尽或交易执行失败时，不应扣减次数。

对于材料核验，事件记录 `MATCH` 或 `MISMATCH`；对于查看和下载，事件记录对应的操作类型及授权准许结果，不虚构材料比对结论。

链上留痕能够证明平台提交了一次经过合约授权检查并完成记账的操作请求，但不能单独证明核验方实际阅读了文件，或完整接收了下载内容。

### 4.2 重复请求与并发请求

每次新的逻辑访问操作生成一个唯一 `requestId`。如果该操作因网络超时而重试，必须沿用原来的 `requestId`，不能把重试当成新的访问操作。

系统需要保证：

- 同一个 `requestId` 不会造成重复扣减授权次数；
- 不同的实际访问操作使用不同的 `requestId`；
- 授权次数只由合约在链上交易中扣减，后端不能采用“先读取剩余次数、再自行减一”的方式作为最终扣次；
- 并发交易由联盟链按共识顺序执行，合约中的扣减操作按交易顺序生效。

若同一 `requestId` 对应的交易已经成功，后端在重试时应查询并返回该次操作的既有结果，而不是把重复提交解释成一次新的成功访问。具体的请求标记、查询和返回机制在合约及后端实现阶段确定。

### 4.3 回执复核：只读流程

回执复核与授权使用原始材料不同。复核人只需要持有回执 PDF 和存证编号，不需要获得存证用户的授权。

流程如下：

```text
复核人输入存证编号，并上传自己持有的回执 PDF
    │
    ▼
后端计算所上传 PDF 原始字节的 SHA-256
    │
    ▼
只读查询链上该存证编号对应的回执摘要
    │
    ▼
比较上传 PDF 摘要与链上回执摘要
    │
    ▼
返回一致 / 不一致
```

该过程只回答：**复核人手中的这份回执 PDF，是否与链上登记的回执摘要一致。**

它不证明原始借条、聊天记录或其他材料在上链前就是真实的，也不证明复核人曾经访问或阅读过原始材料。该流程不提交链上交易、不消费授权次数，也不产生链上访问留痕。

### 4.4 两种操作的对照

| 对比项 | 授权使用：核验、查看、下载 | 回执复核 |
|---|---|---|
| 操作对象 | 原始凭证材料 | 回执 PDF |
| 是否需要存证用户授权 | 需要 | 不需要 |
| 是否上传待比对材料 | 材料核验时需要；查看、下载按业务流程处理 | 需要上传回执 PDF |
| 是否写链 | 是 | 否，只读查询 |
| 是否扣授权次数 | 是 | 否 |
| 能说明什么 | 某次操作通过授权检查并完成链上记账；材料核验可返回一致或不一致 | 手中回执 PDF 与链上登记的回执摘要一致或不一致 |
| 不能说明什么 | 不能证明核验方本人实际阅读或完整接收文件 | 不能证明原始材料上链前真实，也不能证明发生过原文访问 |

## 5. 平台管理员的数据流

### 5.1 初始部署

平台管理员负责完成系统部署和运行环境配置，主要包括：

1. 部署 MySQL 数据库并创建业务表；
2. 配置平台主密钥 KEK；
3. 部署 FISCO BCOS 4 节点本地联盟链；
4. 部署单个 `EvidenceStore` 智能合约；
5. 配置平台服务账户及合约白名单；
6. 配置后端连接信息、合约地址和文件大小限制；
7. 启动 Spring Boot 后端与 Vue 前端。

四个 PBFT 节点部署在同一台主机上，属于单机模拟联盟环境，不代表四个独立机构或四个独立故障域。论文中的可用性与性能结论只适用于该单机实验环境。

### 5.2 主密钥管理

每个原始文件使用独立随机数据密钥 DEK 进行 AES-256-GCM 加密。DEK 再由平台主密钥 KEK 包裹后存入 MySQL。KEK 通过环境变量或权限受限的密钥文件注入服务运行环境，不写入数据库和代码仓库，也不与业务数据放在同一份备份中。

- KEK 泄露：需要更换 KEK，并对仍需保留的 DEK 重新包裹；
- KEK 丢失：相应密文可能无法恢复；
- 用户下载原文：后端在完成身份和授权检查后，使用服务端密钥解密并返回文件。

该模式属于服务端密钥托管。平台在技术上具备解密能力，不能描述为平台无法接触明文。

### 5.3 管理功能

| 管理功能 | 主要内容 | 是否直接写链 |
|---|---|---|
| 用户管理 | 查看用户、启停账号、分配角色 | 否 |
| 区块链管理 | 查看链连接状态、区块高度、合约地址和近期交易 | 只读 |
| 系统设置 | 管理场景字典、算法标识和上传大小上限；合约地址等部署参数以只读展示为主 | 通常否 |
| 合约与白名单运维 | 部署合约、维护平台服务账户白名单 | 是，由部署或运维操作完成 |
| 待上链记录处理 | 查询待上链凭证、检查交易状态并按规则重试 | 可能提交登记交易 |
| 链库一致性巡检 | 根据链上交易和事件核对、修复链下索引记录 | 以只读查询和链下回灌为主 |
| 删除审计 | 记录申请人、处理时间、删除对象及处理结果 | 删除操作涉及链上失效标记 |
| 数据备份 | 备份 MySQL 密文数据及联盟链数据目录 | 否 |

管理员页面不提供任意修改链上历史摘要或伪造用户授权的普通操作入口。平台账户代发交易的事实和平台密钥托管的信任边界应在论文中明确说明。

## 6. 链上与链下的数据边界

系统遵循一个基本原则：**原始文件和可识别个人的业务信息保存在链下；链上只保存完成摘要核验、授权管理和操作追溯所必需的数据。**

| 数据类别 | MySQL | 联盟链 | 说明 |
|---|---|---|---|
| 原始文件 | AES-256-GCM 加密后以 LONGBLOB 保存 | 不保存 | 原文不直接上链 |
| 逐文件摘要 | 保存 | 不单独登记 | 用于重算聚合摘要和定位差异 |
| 文件清单聚合摘要 | 保存 | 保存 | 作为存证登记的核心摘要 |
| 存证编号、场景类型、算法标识 | 保存 | 保存必要字段 | 编号应为随机生成的凭证标识 |
| 普通场景业务字段 | 按业务需要保存，并实施访问控制 | 不保存 | 例如非敏感的协议事项、租期等 |
| 身份及金融账户等敏感字段 | 加密保存 | 不保存 | 按敏感个人信息要求处理 |
| DEK | 以 KEK 包裹后的形式保存 | 不保存 | 明文 DEK 只在必要的内存处理期间出现 |
| KEK | 不入库，部署时注入 | 不保存 | 由平台部署者管理 |
| 授权关系与配额 | 保存查询所需的链下关联信息 | 保存权威授权状态 | 包括假名化核验方标识、有效期、次数和撤销状态 |
| 核验、查看、下载事件 | 保存查询索引或回灌记录 | 保存事件 | 包括 requestId、actionType、时间和结果等必要信息 |
| 回执 PDF | 保存原始 PDF 字节 | 不保存 PDF，仅保存回执摘要 | 复核时由第三方上传自己的 PDF 计算摘要 |
| 用户账号、身份映射 | 保存并进行权限保护 | 不保存直接身份明文 | 假名化标识如可重新关联个人，仍按个人信息管理 |

### 6.1 链上登记内容与授权审计内容要分开理解

存证登记交易主要保存：

- 随机存证编号；
- 文件清单聚合摘要；
- 场景类型；
- 摘要算法标识；
- 合约登记所需状态。

授权和访问管理是另一类链上数据，主要包括：

- 存证编号；
- 被授权方的假名化标识；
- 授权有效期、使用次数和撤销状态；
- 访问请求编号 `requestId`；
- 操作类型 `actionType`；
- 操作时间及必要的处理结果。

因此，不能笼统地说“链上只存一个文件哈希”，也不能说“所有业务信息都上链”。链上数据应限于完成存证登记、授权管理和访问留痕所必需的最小范围。

## 7. 主要状态与异常处理

### 7.1 凭证状态

| 状态 | 含义 | 允许的主要操作 |
|---|---|---|
| 待上链 `PENDING` | 链下数据已保存，尚未获得链上登记确认 | 查询状态、按交易状态进行重试 |
| 已上链 `ON_CHAIN` | 链上登记已确认，链下记录与链上摘要核对一致 | 签发授权、申请回执、授权核验和访问 |
| 已失效 `DISABLED` | 用户删除申请已处理，或凭证按规则被标记为失效 | 禁止新的核验、查看和下载 |

`PENDING` 不能被展示为存证成功。`DISABLED` 不意味着链上历史记录被删除，只表示该凭证不再允许继续进行相关业务操作。

### 7.2 授权状态

授权的有效性由合约状态决定，主要检查：

- 授权是否存在；
- 当前区块时间是否超过有效期；
- 授权是否已撤销；
- 已使用次数是否达到配额；
- 对应凭证是否已失效。

MySQL 中可以保存授权状态的查询副本，但合约状态是最终判断依据。

### 7.3 关键异常处理

| 异常情况 | 处理方式 |
|---|---|
| 文件上传或加密失败 | 不提交链上登记，清理本次未完成的临时数据 |
| 数据库事务失败 | 不提交链上登记 |
| 链上登记明确失败 | 保持未确认状态，记录失败原因，不向用户显示存证成功 |
| 链上交易超时或响应丢失 | 先查询交易哈希、存证编号和链上状态，再决定是否重试 |
| 链上授权已撤销，但 MySQL 尚未同步 | 以合约执行结果为准，拒绝本次操作，并修正链下状态 |
| 同一访问请求重试 | 沿用原 requestId，查询并返回原操作结果，避免重复扣次 |
| 并发访问导致配额竞争 | 合约内检查并扣减次数，不能由后端先查后改 |
| 删除凭证 | 删除链下密文和密钥关联，同时链上标记凭证失效并阻断未结束授权 |
| 核验方上传临时文件 | 仅用于计算摘要和比较，处理结束后清理，不作为平台长期保存的原始凭证 |

## 8. 合约职责与后端接口边界

### 8.1 智能合约负责什么

单个 `EvidenceStore` 合约集中实现以下功能：

| 功能 | 主要职责 |
|---|---|
| 存证登记 | 保存存证编号、聚合摘要、场景类型和算法标识；拒绝重复登记 |
| 授权签发 | 保存核验方假名化标识、有效期和使用次数 |
| 授权撤销 | 将指定授权标记为撤销 |
| 凭证失效 | 将凭证标记为失效，阻止后续授权使用 |
| 授权访问记账 | 检查授权有效性，按 `actionType` 记录核验、查看或下载，并在成功交易中扣减次数 |
| 回执摘要登记 | 将存证编号与最终 PDF 的摘要关联，每个编号仅允许登记一次 |
| 只读查询 | 查询凭证登记信息、授权状态和回执摘要 |

合约不接收原始文件，不读取 MySQL，也不负责计算文件 SHA-256。文件摘要计算、清单聚合和材料差异比较均由 Java 后端完成。

### 8.2 后端负责什么

后端负责：

- 用户登录与 JWT 鉴权；
- 凭证归属和业务字段校验；
- 文件摘要计算、聚合和加密；
- MySQL 数据写入与查询；
- 调用合约并处理交易回执；
- 核验方上传文件的摘要计算和差异比较；
- PDF 回执生成、保存和下载；
- 链上事件同步到链下查询记录；
- 失败重试、状态核对和审计。

### 8.3 接口划分原则

前端只调用后端 REST API，不直接连接联盟链，也不持有平台密钥。后端通过统一的 ChainGateway 调用合约。接口路径和 DTO 字段在详细设计阶段确定，本文不把示例路径视为最终 API 规范。

## 9. 数据库设计范围

数据库按业务实体划分，不为四类场景分别建立四套重复的核心表。四类场景共用凭证主表，场景差异通过场景类型和扩展字段表达。

| 数据表 | 主要内容 | 说明 |
|---|---|---|
| `user` | 用户账号、口令哈希、角色、账号状态 | 不保存明文口令 |
| `evidence` | 存证编号、创建者、场景类型、聚合摘要、业务时间声明、链上状态、交易哈希和区块高度 | 凭证主表 |
| `evidence_file` | 文件标识、文件名、MIME 类型、大小、逐文件摘要、IV、密文、包裹后的 DEK | 原始文件密文存入 LONGBLOB |
| `evidence_field` 或扩展字段 | 场景业务字段 | 敏感身份及金融账户字段单独加密；其他字段按权限控制 |
| `grant_auth` | 凭证、核验方标识、有效期、配额、使用次数、撤销状态 | 链上授权状态的链下查询记录 |
| `verify_log` | requestId、操作类型、交易信息、处理结果和时间 | 由链上事件或交易结果回灌 |
| `receipt` | 最终 PDF 原始字节、回执摘要、存证编号及登记状态 | 下载返回已保存的原始 PDF |
| `sys_config` | 文件大小限制、算法标识、合约地址等配置 | 部署参数与业务配置分开管理 |
| `audit_log` | 管理操作、删除申请及处理过程 | 用于链下审计 |

以上为逻辑表范围。实际实现时可以根据 MyBatis-Plus 映射和查询需要调整字段、索引及关联方式，但不改变链上链下的数据边界。

## 10. 安全、隐私与系统边界

### 10.1 文件加密

原始文件逐个使用随机 DEK 进行 AES-256-GCM 加密。每次文件加密使用独立随机 IV，并通过 AAD 将密文绑定到对应存证编号和随机文件标识。DEK 再由 KEK 包裹，包裹过程也使用独立随机 IV。

文件密文、IV、认证标签和包裹后的 DEK 保存在 MySQL。姓名、身份证号、银行账号等敏感字段应单独加密保存；普通业务字段按访问权限进行保护，不应笼统描述为所有业务字段均采用相同加密方式。

### 10.2 个人信息保护

系统不把姓名、手机号、身份证号、银行账号、相对方身份等直接身份信息写入链上。链上使用随机凭证编号和假名化核验方标识；如果链下仍存在可关联到个人的映射，相关数据仍应按个人信息进行管理。

演示与测试材料使用脱敏或合成数据。真实个人信息处理应遵循任务书和开题报告所引用的个人信息保护法要求，包括处理依据、告知、敏感个人信息单独同意、查阅复制和删除等事项。

### 10.3 证明能力边界

系统可以提供的技术材料包括：

- 文件在存证登记时对应的摘要；
- 链上登记交易、区块高度及合约存储记录；
- 核验方上传材料与已登记摘要之间的一致或不一致结果；
- 授权签发、撤销和授权使用记录；
- 回执 PDF 与链上回执摘要的一致性结果。

系统不能仅凭上链就证明：

- 文件在上传前没有被伪造或编辑；
- 文件中记载的借贷、租赁或协议事实真实发生；
- 用户填写的业务时间真实；
- 核验方本人实际阅读或完整接收了文件；
- 系统具有法定公证机构的公证效力。

区块时间依赖节点本地时钟，应作为链上记录时间和相对顺序参考，不应表述为独立第三方可信时间戳。

## 11. 测试内容与设计点对应关系

| 测试方向 | 主要测试内容 | 预期结果 |
|---|---|---|
| 文件摘要 | 流式 SHA-256 与标准工具计算结果比较 | 摘要一致 |
| 聚合摘要 | 文件重命名、调整上传顺序、增删文件、重复文件 | 重命名和换序不改变聚合摘要；内容或文件集合变化会改变摘要 |
| 加密 | 修改密文、错误 AAD、错误密钥或 IV | 完整性校验失败，不能正常解密 |
| 存证登记 | 正常登记、重复编号、空文件清单、链连接失败 | 重复编号和空清单被拒绝；未确认交易不显示为存证成功 |
| 授权管理 | 正常授权、非凭证创建者授权、撤销、过期、次数用尽 | 非法授权被拒绝；撤销和过期后不能继续使用 |
| 授权扣次 | 同一 requestId 重试、不同 requestId 并发访问 | 重试不重复扣次；并发情况下使用次数不超配额 |
| 核验比较 | 材料一致、单文件替换、文件缺失、文件新增、数据库摘要清单被篡改 | 返回正确的一致性结论；数据库摘要清单与链上摘要不一致时不继续信任其差异定位结果 |
| 回执 | PDF 生成、保存、下载、第三方上传复核、重复登记 | 下载字节与已保存 PDF 一致；上传 PDF 摘要与链上登记值可比较；重复登记被拒绝 |
| 删除 | 删除密文与包裹密钥、凭证失效、授权阻断 | 链下原文不能经正常业务流程恢复；失效凭证不能继续核验、查看或下载 |
| 权限控制 | 未登录、越权访问、非白名单服务账户调用 | 未授权请求被拒绝 |

## 12. 实施顺序

为控制本科毕业设计的工作量，按业务主线逐步实现，不额外引入微服务、消息队列、缓存中间件或对象存储。

1. **基础框架：**搭建 Vue、Spring Boot、MySQL，完成登录、角色权限和四类场景动态表单。
2. **文件处理：**实现逐文件 SHA-256、清单聚合、AES-GCM 加密和数据库保存，先完成单元测试。
3. **链上登记：**搭建 FISCO BCOS 四节点环境，部署单个合约，完成存证登记与只读查询。
4. **授权管理：**实现授权签发、撤销、有效期和使用次数检查。
5. **授权使用：**实现材料核验、查看和下载的链上记账，处理 requestId 重试与并发扣次。
6. **回执：**实现 PDF 两阶段生成、原始字节保存、回执摘要登记和第三方上传复核。
7. **删除与管理：**实现凭证失效、授权阻断、删除审计、链状态查看和必要的巡检功能。
8. **测试与文档：**完成四类场景主流程、权限测试、篡改对照实验和论文材料。

技术版本以第一周最小联调结果为准：先验证四节点链、单合约部署和 Java SDK 读写，再锁定 JDK、FISCO BCOS、Java SDK、Spring Boot 与 Solidity 编译器版本。版本组合未经实测前不写成已验证事实。

## 14. 需要在实现阶段确认的事项

以下事项属于实现或联调阶段需要验证的内容，不应在设计说明中提前写成已完成：

- 单机 4 节点联盟链与 Spring Boot、MySQL 同时运行时的实际内存占用；
- FISCO BCOS、Java SDK、JDK、Spring Boot 和 Solidity 编译器的兼容组合；
- 当前部署环境中的官方建链脚本和节点二进制能否正常运行；
- MySQL LONGBLOB、`max_allowed_packet`、Spring Boot multipart 限制与实际文件上限是否匹配；
- 链上交易超时、响应丢失时，如何通过交易哈希、存证编号和事件查询确认交易最终状态；
- requestId 的唯一性范围、合约判重状态与后端查询原操作结果的具体实现。

这些事项不改变本设计的基本原则：链上状态作为存证与授权的最终依据；原始文件密文保存在 MySQL；所有链上写操作由平台服务账户提交；授权次数由合约原子扣减；回执复核只读，不消费授权。
